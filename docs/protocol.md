# Общий контракт frontend ↔ backend: JSON v1

Источник: [`shared-infinite-canvas-mvp-spec.docx`](../shared-infinite-canvas-mvp-spec.docx), версия 1.0 от 16.11.2026. Рабочие задания: [frontend](frontend.md), [backend](backend.md).

Бинарный профиль реализован отдельно: [MessagePack v2](protocol-v2-msgpack.md). JSON v1 продолжает работать без subprotocol и с `endless-drawing.json.v1`. Семантика операций ниже общая, формы v2 после decode совпадают, кроме версии hello.ack.

Manifest/missing geometry — [v3](protocol-v3-manifest.md); приоритет видимой области — [v4](protocol-v4-priority.md). Семантика мутаций общая; форма подписки и порядок geometry определяются выбранным профилем.

## 1. Статус и решения перед интеграцией

**Из исходного ТЗ:** один WSS `/ws` на вкладку, JSON с `type`, `hello`, подписки по bounds, snapshot begin/chunk/end, create/delete, ack/error, `request_id`, `subscription_id`, ownership через сессионный секрет и идемпотентность создания по UUID.

**Предлагаемая детализация, а не уже согласованные требования исходника:** точные payload серверных сообщений ниже, `hello.ack`, поля ack/error, коды ошибок, поведение повторного удаления, `resync_required`, лимит chunk в 1000, геометрические стили и запас bounds. Эта детализация уже реализована в backend и доступна frontend для интеграции; отличия от исходного DOCX всё ещё нужно принять обеим сторонам либо изменить здесь совместно.

В исходнике также не заданы точные лимиты протяжённости штриха, viewport, подключения, очередей и таймаутов. Backend выбирает конфигурируемые безопасные значения и документирует их; ограничения, влияющие на UX, согласуются с frontend.

## 2. Транспорт и общие типы

- Production: HTTPS + WSS, один origin для приложения и `/ws`.
- Dev: допустимы HTTP/WS на localhost; согласовать порт и proxy Vite.
- Каждое WS-сообщение — один JSON-объект в текстовом frame.
- Первое прикладное сообщение — `hello`. До его успешной проверки подписки и мутации запрещены.
- `session_secret`: base64url без padding, ровно 32 случайных байта после декодирования. Клиент генерирует через Web Crypto, хранит в `sessionStorage`.
- UUID штриха генерирует клиент. `request_id` коррелирует конкретную попытку операции, но не заменяет UUID для идемпотентности.
- `subscription_id` уникален для каждой новой подписки в соединении. Одновременно активна одна область; новая подписка заменяет старую.
- Все координаты и числовые настройки — конечные JSON numbers; координаты в `[-1e9, 1e9]`.
- `seq` — положительный серверный порядок создания. В примерах и исходнике это JSON number; для совместимости с JS сервер должен выдавать только безопасные целые (`<= Number.MAX_SAFE_INTEGER`). Переход на строковое представление потребует совместного изменения контракта.
- `seq` удалённого штриха остаётся его исходным `seq`, **это не курсор событий**.
- Ownership, bounds, время, статус удаления и `seq` вычисляет сервер. Клиент не управляет ими.

Публичный объект:

```json
{
  "id": "87a122fa-7537-4b88-9b77-b45d24a29714",
  "seq": 101,
  "points": [[-14.5, 2], [-8, 4.2], [0, 9]],
  "brush": "round",
  "width": 6,
  "color": "#202020",
  "opacity": 0.8,
  "own": true
}
```

`own` вычисляется отдельно для каждого получателя по секрету его соединения. `owner_digest` и секрет никогда не попадают в публичный объект. Один и тот же штрих автор получает с `own: true`, независимый посетитель — с `own: false`.

Область:

```json
{"min_x": -800, "min_y": -600, "max_x": 800, "max_y": 600}
```

Обе оси должны иметь `min < max`, значения ограничены диапазоном мира. Сервер также ограничивает размер области для защиты от запроса всего мира.

## 3. Установка соединения

Клиент:

```json
{"type":"hello","session_secret":"<base64url-32-random-bytes>"}
```

Предлагаемый ответ сервера:

```json
{"type":"hello.ack","protocol_version":1}
```

Необязательное поле `spawn` — подсказка точки входа для новой сессии (не для reload/reconnect, это решает клиент):

```json
{"type":"hello.ack","protocol_version":1,"spawn":{"x":5012.5,"y":-6990.25}}
```

Сервер раз в `SPAWN_REFRESH_MS` (по умолчанию 30 с) выбирает до 64 случайных живых штрихов (равномерно по `seq` через уникальный индекс) и держит центры их bounds в памяти; `spawn` = случайный из них ± 400 world units по каждой оси, внутри мира. Чем больше нарисовано в области, тем вероятнее туда попасть, и по мере расползания рисунка точки входа расходятся. В пустом мире поле отсутствует. Подсказка не раскрывает ничего, кроме публичных bounds; камера клиента на сервер по-прежнему не передаётся. Старый клиент поле игнорирует.

После этого клиент может подписываться и отправлять мутации. Повторный `hello` для смены владельца в открытом соединении не поддерживается: открыть новое соединение. Не логировать hello или исходные тела WS-сообщений.

## 4. Подписка и snapshot

Клиент:

```json
{
  "type": "viewport.subscribe",
  "subscription_id": "v12",
  "bounds": {"min_x": -800, "min_y": -600, "max_x": 800, "max_y": 600}
}
```

Сервер, предлагаемые точные формы:

```json
{"type":"viewport.snapshot.begin","subscription_id":"v12"}
```

```json
{
  "type": "viewport.snapshot.chunk",
  "subscription_id": "v12",
  "strokes": [
    {
      "id":"87a122fa-7537-4b88-9b77-b45d24a29714",
      "seq":101,
      "points":[[0,0],[10,5]],
      "brush":"round",
      "width":6,
      "color":"#202020",
      "opacity":0.8,
      "own":false
    }
  ]
}
```

```json
{"type":"viewport.snapshot.end","subscription_id":"v12"}
```

- Пустая область: begin → end, без chunks.
- Непустая: chunks в порядке возрастания `seq`, предлагаемый предел — **до 1000 штрихов**, дополнительно ограничивать размер сериализованного chunk в байтах. Большой штрих не должен приводить к гигантскому пакету из 1000 объектов.
- Сервер сам продолжает выборку до полного снимка области: клиент не посылает отдельный запрос каждой страницы.
- Число chunks не ограничено одной страницей; ограничены очередь и ресурсы соединения.
- Snapshot включает все неудалённые штрихи, чьи серверные bounds пересекают область. Отдаются целые штрихи, без обрезки точек.
- Снимок должен иметь согласованную границу с событиями. Создания/удаления во время snapshot буферизуются и отдаются после end; не должно быть пропусков подтверждённых изменений.
- Все snapshot-сообщения и scoped-события несут `subscription_id`; поздние сообщения старой подписки клиент игнорирует.
- При новой подписке начать новый snapshot и завершить/отменить прежнюю загрузку без смешивания наборов.
- Клиент заменяет авторитетное состояние области новым снимком, а не только добавляет новые id в старый кеш.

## 5. Создание

Клиент:

```json
{
  "type":"stroke.create",
  "request_id":"r1",
  "stroke":{
    "id":"87a122fa-7537-4b88-9b77-b45d24a29714",
    "points":[[0,0],[10,5]],
    "brush":"round",
    "width":6,
    "color":"#202020",
    "opacity":0.8
  }
}
```

Предлагаемый ack автору после успешного коммита:

```json
{
  "type":"ack",
  "request_id":"r1",
  "operation":"stroke.create",
  "stroke":{
    "id":"87a122fa-7537-4b88-9b77-b45d24a29714",
    "seq":101,
    "points":[[0,0],[10,5]],
    "brush":"round",
    "width":6,
    "color":"#202020",
    "opacity":0.8,
    "own":true
  }
}
```

Событие подписчикам пересекающейся области:

```json
{
  "type":"stroke.created",
  "subscription_id":"v12",
  "stroke":{
    "id":"87a122fa-7537-4b88-9b77-b45d24a29714",
    "seq":101,
    "points":[[0,0],[10,5]],
    "brush":"round",
    "width":6,
    "color":"#202020",
    "opacity":0.8,
    "own":false
  }
}
```

Ack отправляется автору независимо от текущей области. Автор может также получить `stroke.created`; клиент дедуплицирует по `id` и не добавляет второй элемент undo. На взаимный порядок ack и scoped-event полагаться нельзя: при snapshot событие может быть задержано.

### Идемпотентность — предлагаемое уточнение

- Тот же UUID, тот же владелец и те же нормализованные точки/параметры: вернуть существующий объект, не менять `seq`, не вставлять новую запись и не публиковать новое создание.
- Тот же UUID с другим содержимым: `id_conflict`.
- Тот же UUID другого владельца: `id_conflict`, без передачи его секретных данных и без присвоения ownership.
- Повтор create уже мягко удалённого UUID: `stroke_deleted`, не воскрешать объект и не создавать новый.
- Сравнение содержимого: числовые значения точек/width/opacity, порядок точек, brush и нормализованный регистр цвета; не побайтовое сравнение исходного JSON. Сервер не меняет траекторию.
- Для повторной отправки после потери ack клиент сохраняет UUID и payload; `request_id` может быть новым.

## 6. Удаление

Клиент:

```json
{"type":"stroke.delete","request_id":"r2","stroke_id":"87a122fa-7537-4b88-9b77-b45d24a29714"}
```

Предлагаемый ack автору:

```json
{
  "type":"ack",
  "request_id":"r2",
  "operation":"stroke.delete",
  "stroke_id":"87a122fa-7537-4b88-9b77-b45d24a29714",
  "seq":101,
  "already_deleted":false
}
```

Событие подписчикам области, пересекающей **исходный bounds удалённого штриха**:

```json
{
  "type":"stroke.deleted",
  "subscription_id":"v12",
  "stroke_id":"87a122fa-7537-4b88-9b77-b45d24a29714",
  "seq":101
}
```

- Ластик и undo используют одну операцию; удаление всего штриха, не его сегмента.
- Авторизация выполняется по digest секрета соединения, включая повторы и уже удалённые записи.
- Предложение: повтор удаления собственного удалённого UUID возвращает ack с `already_deleted: true`, без нового события; неизвестный UUID — `not_found`; чужой — `forbidden`.
- UI не должен интерпретировать отсутствие объекта в текущем snapshot как доказательство удаления объекта во всём мире.
- Административное скрытие создаёт такое же публичное событие удаления, без раскрытия служебных данных.

## 7. Ошибки, ограничения, resync

Предлагаемая форма ошибки мутации:

```json
{"type":"error","request_id":"r2","code":"forbidden","message":"Stroke cannot be deleted"}
```

Для ошибки подписки указать `subscription_id`; для некоррелируемой ошибки hello/формата оба корреляционных поля можно опустить. `message` — безопасное пояснение для диагностики, клиентская логика опирается на `code`.

| Предлагаемый code | Смысл / действие |
| --- | --- |
| `invalid_message` | Неверный JSON, тип или структура |
| `invalid_session` | Секрет не декодируется в 32 байта |
| `hello_required` | Операция до завершения hello |
| `validation_failed` | Недопустимый штрих или bounds |
| `forbidden` | Попытка удалить чужое |
| `not_found` | UUID для удаления отсутствует |
| `id_conflict` | UUID занят другим содержимым/владельцем |
| `stroke_deleted` | Попытка повторного create удалённого UUID |
| `rate_limited` | Превышена частота; возможен повтор с задержкой |
| `message_too_large` | Слишком большой payload; транспорт также может закрыть WS с кодом 1009 без JSON-ошибки |
| `resync_required` | Нельзя гарантировать продолжение потока; получить новый snapshot |
| `internal_error` | Внутренняя ошибка без SQL, секретов или stack trace |

При переполнении очереди сервер не должен молча терять события: если возможно, отправить `resync_required` с текущим `subscription_id`, затем отменить подписку; при невозможности доставки закрыть соединение. Клиент заново подписывается либо реконнектится. Повторные медленные загрузки требуют уменьшения нагрузки, а не бесконечного накопления памяти.

Реконнект всегда проходит через hello и новый snapshot. В v1 нет восстановления потока по last seq: удаления не получают нового `seq`, поэтому такой курсор пропускал бы изменения.

Первоначальные пределы из исходника, конфигурируемые на сервере:

- от 1 до 2000 точек на штрих;
- входящее WS-сообщение не более 128 KiB;
- не более 5 завершённых штрихов в секунду на соединение;
- ширина `[1, 64]`, opacity `(0, 1]`, `round | square | chisel | spray` (последние два — миграция 0003), цвет `#RRGGBB`;
- дополнительные лимиты протяжённости, подключений, удалений, подписок, очередей и таймаутов.

## 8. Предлагаемые геометрические договорённости

Эти детали необходимо принять обеим сторонам до теста bounds и визуальной приёмки:

- Round: Canvas `lineCap = "round"`, `lineJoin = "round"`.
- Square: Canvas `lineCap = "square"`, `lineJoin = "bevel"`, чтобы не создавать длинные miter-выбросы.
- Одиночная точка: круг либо квадрат с центром в точке; для квадратной точки стороны параллельны мировым осям.
- Цвет нормализуется сервером в верхний регистр `#RRGGBB`.
- Bbox сервер считает по min/max координат с расширением наружу. Для round достаточно `width / 2 + epsilon`.
- **Важный нюанс:** у наклонной линии Canvas square-cap угол может выступать по оси больше чем на `width / 2`. Если выбран этот renderer, предлагается консервативное расширение для square: `width / sqrt(2) + epsilon`, где `epsilon = 1` мировая единица. Это уточнение исходного правила «половина ширины и запас», чтобы квадратные концы не исчезали у границ.
- Chisel (плоский наконечник -45°): тот же запас, что у square, `width / sqrt(2) + 1`. Spray v1 (частицы внутри диска диаметром width, seed из lowercase UUID): запас round `width / 2 + 1`. Дополнительных полей в create нет; алгоритм — `../endless-drawing-frontend/docs/brushes.md`.
- Bbox одиночной точки всегда непустой. На пределе мира допустимые точки остаются в диапазоне, вычисленный bounds может выходить за него на запас кисти; сервер не обрезает геометрию.

## 9. HTTP и приёмка контракта

Обязательно:

- `GET /` — приложение;
- `GET /healthz` — жив ли процесс;
- `GET /readyz` — готов ли сервис, включая проверку БД.

**Необязательно:** `GET /api/v1/strokes?min_x=...&min_y=...&max_x=...&max_y=...&after_seq=...&limit=...`. В базовом MVP предлагается не реализовывать: основной путь — WS snapshot. Если ручка понадобится, отдельно согласовать response, пагинацию и передачу секрета через Authorization, никогда через URL. Не создавать второй независимый механизм live-подписки.

Минимальный совместный smoke-test:

1. Два соединения с разными секретами получают снимок одной области.
2. Первое создаёт штрих: ack с `own: true`, второе получает событие с `own: false`.
3. Повтор create не создаёт новый объект; чужое delete отклоняется.
4. Собственное delete убирает объект у обоих; повтор delete безопасен.
5. Создание и удаление во время многочастного snapshot не теряются.
6. Реконнект и новый snapshot удаляют устаревшее состояние; поздняя старая подписка игнорируется.

## 10. Реализованный профиль backend

Backend реализует приведённые выше wire-формы: `hello.ack`, begin/chunk/end, ack с `operation`, события с `subscription_id` и ошибки с безопасным `message`. HTTP-выборки штрихов нет. Административное скрытие пока не реализовано.

- Локальный endpoint: `ws://127.0.0.1:3000/ws`; production — WSS того же домена.
- Origin обязателен и должен точно совпадать с `ALLOWED_ORIGINS`; без Origin/при запрещённом Origin Upgrade возвращает 403. Браузер выставляет его сам, CLI/Node-клиент — явно.
- `request_id` / `subscription_id`: непустые строки до 128 байт UTF-8. Каждая новая подписка должна иметь новый id; сервер не ведёт бесконечную историю идентификаторов.
- Некорректные структуры/неизвестные клиентские поля отклоняются; серверные поля не принимаются в `stroke.create`. Повторный hello не меняет владельца соединения.
- Конечные f64 проходят round-trip JSONB без смены числового содержимого; цвет нормализуется в верхний регистр.
- Начальные размеры: максимум 128 KiB входящего сообщения/frame, 100 объектов на страницу snapshot, максимум 256 KiB на сериализованный chunk. Пустой снимок — begin/end без пустого chunk.
- Начальный предел viewport — 30000 единиц по каждой оси, штриха — 100000 по каждой оси до brush padding. Проверяются обе оси, а не только площадь.
- Rate limits на соединение: create 5/с, delete 20/с, subscribe 5/с, все frames после hello суммарно 100/с. Окно скользящее. Недопустимый структурно корректный stroke тоже расходует create-лимит.
- Не более 256 открытых/ожидающих hello соединений; исчерпание даёт HTTP 503. Ограничения по IP ещё предстоит добавить перед публичным запуском.
- Hello ожидается до 5 секунд, отправка одного пакета — до 5 секунд, ожидание команды — до 10 секунд, весь snapshot — до 30 секунд. Ping каждые 20 секунд, отключение после 60 секунд без входящих frames.
- Мутации проходят один actor; после commit публикуется событие и формируется ack. Успешный retry не публикует новое событие.
- Барьер snapshot внутри actor устанавливает REPEATABLE READ снимок через фактический запрос `pg_current_snapshot()`, затем подписывает receiver на события. Во время выдачи chunks события остаются в ограниченном broadcast-ring; после end идут в live-поток.
- При overflow ring, ошибке/таймауте snapshot сервер отправляет `error` с `code: "resync_required"` и текущим `subscription_id`, отменяет подписку. Клиент отбрасывает незавершённый staging и запрашивает новый snapshot с новым id. Если отправка невозможна — соединение закрывается.
- Слишком большой/повреждённый транспорт может закрыть соединение без JSON-ошибки. Клиент не должен ожидать обязательный `message_too_large`.
- Отсутствие ack при timeout/disconnect допускает успешный commit: повтор create только с тем же UUID и содержимым. После reconnect всегда hello + новый snapshot.

Все параметры, верхние защитные пределы конфигурации и dev-команды описаны в [README](../README.md). Адреса, capacity и численные ограничения не являются обещанием поддержки конкретного числа активных посетителей: требуется нагрузочный тест.
