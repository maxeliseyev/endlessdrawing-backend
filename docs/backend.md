# Backend: общий бесконечный холст, MVP

Рабочее ТЗ для backend-разработчика.

- Источник: [`shared-infinite-canvas-mvp-spec.docx`](../shared-infinite-canvas-mvp-spec.docx), версия 1.0 от 16.11.2026.
- Смежные документы: [frontend](frontend.md), [общий контракт v1](protocol.md).
- Требования исходника обязательны. Дополнения wire-контракта явно обозначены в `protocol.md` как предложения для согласования.

## 1. Результат и ограничения архитектуры

Сделать один серверный процесс, который раздаёт приложение, хранит векторы общего мира в PostgreSQL, загружает области через WebSocket и рассылает завершённые создания/удаления без пропусков.

**Стек:** Rust + Axum + Tokio, SQLx, PostgreSQL. Один пул БД, миграции, типизированные запросы. Один экземпляр backend в MVP.

**Не добавлять:** Redis, брокеры, микросервисы, PostGIS, аккаунты, комнаты, серверное хранение камеры, передачу движений незавершённой кисти, публичную админ-панель.

Backend — источник истины для `seq`, владельца, времени создания/удаления и bounds. Клиентские `own`, `seq`, `bounds`, `owner_digest`, даты не принимаются как доверенные данные. Пользовательский API создания принимает только поля из согласованного контракта.

## 2. Поверхность API

| Endpoint | Назначение |
| --- | --- |
| `GET /` и статические ресурсы | Production-сборка Vite-приложения |
| `GET /healthz` | Liveness процесса |
| `GET /readyz` | Readiness с проверкой доступности БД |
| `GET /ws` с Upgrade | Единственное WS-соединение на вкладку |

Предлагаемое поведение probes: `200` при успехе, `/readyz` возвращает `503` при недоступности БД. Формат тела не задан исходником; достаточно минимального стабильного ответа без внутренних деталей.

HTTP-выборка `/api/v1/strokes` в исходнике необязательна; в базовом MVP **предлагается не реализовывать**, если WS полностью покрывает загрузку и синхронизацию. Не делать конкурирующий механизм live-подписок.

JSON-сообщения, поля ack/error, ownership в событиях, идемпотентные повторы и resync реализовать по [общему контракту](protocol.md). При изменении схемы сначала менять этот документ и fixtures для frontend mock.

## 3. Данные и миграции

Минимальная таблица из исходника:

```sql
CREATE TABLE strokes (
    id            uuid PRIMARY KEY,
    seq           bigint GENERATED ALWAYS AS IDENTITY UNIQUE,
    owner_digest  bytea NOT NULL CHECK (octet_length(owner_digest) = 32),
    points        jsonb NOT NULL,
    brush         text NOT NULL CHECK (brush IN ('round', 'square')),
    width         double precision NOT NULL CHECK (width BETWEEN 1 AND 64),
    color         text NOT NULL,
    opacity       double precision NOT NULL CHECK (opacity > 0 AND opacity <= 1),
    bounds        box NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    deleted_at    timestamptz
);

CREATE INDEX strokes_visible_bounds_gist
    ON strokes USING gist (bounds)
    WHERE deleted_at IS NULL;

CREATE INDEX strokes_owner_recent_idx
    ON strokes (owner_digest, seq DESC)
    WHERE deleted_at IS NULL;
```

- Точки — JSONB-массив пар f64. Геометрия остаётся векторной, не сохранять canvas-картинки вместо неё.
- `box`, оператор пересечения `&&`, GiST `box_ops` работают без PostGIS.
- Секрет не сохраняется, только его 32-байтный SHA-256 digest.
- Удаление мягкое: заполнить `deleted_at`, не удалять строку физически в пользовательском пути.
- Tombstone сохраняет UUID, владельца и исходные данные для идемпотентности и безопасных повторов.
- `own` — вычисляемое поле конкретного ответа, не колонка и не общее публичное свойство.
- Пропуски в IDENTITY допустимы; `seq` не обязан быть непрерывным.

Выборка страницы области через bind-параметры:

```sql
SELECT id, seq, points, brush, width, color, opacity,
       owner_digest = $7::bytea AS own
FROM strokes
WHERE deleted_at IS NULL
  AND bounds && box(point($1, $2), point($3, $4))
  AND seq > $5
ORDER BY seq ASC
LIMIT $6;
```

Параметры: min/max X/Y, последний `seq` страницы, лимит, digest текущего соединения. Страницы одного snapshot должны относиться к одной согласованной версии данных; простой набор независимых READ COMMITTED-запросов без барьера и буферизации недостаточен.

SQLx-декодирование PostgreSQL `box` и стратегии типизации запросов проверить отдельным integration-тестом. Допустима безопасная конверсия bounds через bind-параметры; не собирать SQL строковой интерполяцией координат.

## 4. Валидация и защитные лимиты

Проверять до записи в БД:

| Поле / ресурс | Правило |
| --- | --- |
| `id` | Корректный UUID |
| `points` | От 1 до 2000 точек, каждая — ровно пара чисел |
| Координаты | Конечные f64 в `[-1_000_000_000, 1_000_000_000]` |
| `brush` | Только `round` или `square` |
| `width` | Конечное число в `[1, 64]` |
| `color` | Строго `#RRGGBB`, с согласованной нормализацией регистра |
| `opacity` | Конечное число в `(0, 1]` |
| Входящее WS-сообщение | Начальный максимум 128 KiB |
| Create | Начальный максимум 5 завершённых штрихов/сек на соединение |
| Подписка | Конечные упорядоченные bounds, допустимый диапазон и ограниченная площадь/стороны |

Число точек, размер сообщения и rate limits конфигурируемы. Конкретный алгоритм burst/rate limiting документировать.

Дополнительно задать конфигурируемые ограничения:

- геометрическая протяжённость штриха;
- частота подключений и число соединений, включая ограничения по IP;
- частота delete и resubscribe, чтобы create-limit не был единственной защитой;
- размер очереди мутаций, исходящего канала, snapshot-буфера и сериализованных chunks;
- hello timeout, время запросов БД, idle/heartbeat policy и таймаут отправки медленным клиентам.

Точные значения этих дополнительных ограничений исходником не установлены: выбрать, документировать и согласовать влияющие на UX параметры до публичного запуска. При работе за reverse proxy доверять forwarded IP только от настроенных доверенных proxy.

### Bounding box

Считать самостоятельно по точкам и форме/толщине кисти, с расширением для видимой геометрии и запасом округления. Для одной точки bounds непустой. Клиентские bounds не использовать.

Для square-cap требуется учесть выступающие углы наклонных линий, не только `width / 2`: предлагаемые точные стили и консервативная формула согласуются в [контракте](protocol.md#8-предлагаемые-геометрические-договорённости). Протестировать попадание толстых round/square штрихов у границ области, включая одиночные точки.

## 5. Сессия и владение

1. Проверить Origin при WS Upgrade по allowlist; CORS не заменяет эту проверку.
2. Дождаться `hello` в ограниченное время, декодировать ровно 32 случайных байта секрета.
3. Вычислить SHA-256 от исходных байтов секрета и сохранить digest в контексте соединения. Не хешировать разные текстовые представления вместо байтов.
4. При create использовать digest соединения; не принимать произвольный owner/session ID.
5. При delete проверять совпадение digest со строкой БД. Самого `own` от клиента недостаточно.
6. Для каждого snapshot, ack и события формировать `own` относительно получателя.

Чужое delete не меняет БД и возвращает отказ. Проверка обязательна также для удалённых строк и повторов. Повтор create с чужим UUID не присваивает авторство и не раскрывает digest.

Перезагрузка вкладки сохраняет секрет через `sessionStorage`; backend не должен создавать новый обязательный аккаунт/cookie вместо согласованной схемы. Утрата секрета означает утрату пользовательского права удаления; административное скрытие — отдельное исключение.

## 6. Последовательные мутации и публикация

**Критически важно:** IDENTITY выдаёт порядок номеров, но не гарантирует порядок коммитов параллельных транзакций.

В одном серверном процессе сделать **единственный последовательный обработчик мутаций**. Все create, пользовательские delete и административные скрытия проходят через него:

1. Проверить запрос и лимиты, поместить в ограниченную очередь.
2. В последовательном обработчике выполнить проверку текущей записи/ownership и транзакцию.
3. Завершить commit.
4. Только после успешного commit подтвердить операцию и опубликовать соответствующее событие.
5. Затем обрабатывать следующую мутацию с сохранением порядка публикации.

Ни ошибка БД, ни откат транзакции не создают успешный ack или событие. Сбой процесса после commit до доставки лечится новым snapshot и идемпотентным повтором UUID, а не заявлением о exactly-once доставке.

Для create вернуть сохранённый серверный объект. Для delete оставить tombstone и использовать исходные `seq` и bounds для события. Идемпотентные повторы не должны повторно порождать мутации и broadcast.

Не рассылать один заранее сериализованный объект с `own: true` всем подписчикам: ownership зависит от соединения. Внутренние события могут содержать служебные данные, но публичный сериализатор их не раскрывает.

`seq` — порядок создания/отрисовки, не версия всех изменений. Удаление старого штриха не получает новый `seq`. Поэтому нельзя строить reconnect только на `after_seq`.

## 7. Snapshot без пропусков

Одна активная подписка на соединение. Сервер загружает все видимые неудалённые штрихи области порциями и затем передаёт изменения.

**Инвариант:** для выбранной границы состояния клиент получает согласованный снимок плюс все последующие изменения, включая удаления, без окна между SELECT и подключением к broadcast.

Допустимая стратегия:

- согласовать регистрацию подписки, начало буферизации и фиксацию read snapshot с последовательным обработчиком мутаций через барьер;
- читать страницы из одного согласованного snapshot БД, например REPEATABLE READ после фактического установления snapshot, а не только команды BEGIN;
- пока идут begin/chunks, копить последующие изменения для этой подписки в ограниченном буфере;
- отправить end, затем буфер в порядке мутаций и атомарно переключить подписку в live-режим;
- не держать очередь мутаций заблокированной на всё время сетевой отправки снимка.

Внутренняя реализация может быть другой, если интеграционные тесты доказывают тот же инвариант. На границе допустимы дедуплицируемые повторы, но не пропуски.

Требования к ресурсам и доставке:

- Не загружать весь мир и не собирать неограниченный снимок в память.
- Chunk ориентировочно до 1000 штрихов; дополнительно ограничить байтовый размер.
- Штрих выбирается при пересечении серверного bbox с областью, отдаётся целиком.
- Удаление рассылается по bounds исходного штриха, хотя строка уже исключена из active-выборки.
- Новая подписка заменяет предыдущую; все scoped-сообщения содержат `subscription_id`.
- Ack автору доставляется независимо от того, пересекает ли его текущая область изменённый штрих.
- Переполнение буфера, lag в broadcast или медленный клиент не должны приводить к тихой потере событий. Потребовать resync либо закрыть соединение, освободить ресурсы.
- После reconnect всегда новый hello и snapshot. Восстановление по журналу событий в MVP не требуется.

## 8. Административное скрытие и безопасность

**Уточнение владельца после исходного DOCX:** требуется отдельный браузерный `/admin/` и серверная аутентификация **логин + сложный пароль + обязательный WebAuthn/FIDO2**, основной и запасной ключ. Универсальный служебный секрет не заменяет эту схему. Подробные требования и предлагаемый API/аудит/provisioning — в [плане модерации](moderation.md); административные возможности пока не реализованы.

Операция обязана идти через общий обработчик мутаций, выполнить soft delete и разослать `stroke.deleted`. Не ограничиваться прямым UPDATE в БД без уведомления живых клиентов. Для CLI допускаются закрытые provisioning/recovery операции через доверенный SSH, но не password-only обход WebAuthn. Публичной панели нет; admin entry отделён от публичного приложения. Пароли/сессионные секреты не попадают в JS-сборку, VITE/Storage/URL и обычный WS hello.

Обязательно:

- TLS на reverse proxy, снаружи только HTTPS/WSS; PostgreSQL не опубликован в Интернет.
- Проверка Origin, payload limits, rate limiting, ограничения времени и памяти.
- Логи без `session_secret`, Authorization, исходных тел WS и чувствительных connection context.
- Ошибки клиенту без SQL, DSN, внутренних трассировок и digest.
- Служебный аудит скрытия без секретов; политика доступа к нему документирована.
- Регулярные резервные копии PostgreSQL и проверка восстановления.
- Правила модерации и хранения данных утверждает владелец до публичного запуска; приложение само их не придумывает.

## 9. Локальный запуск и деплой

Исходник предлагает `frontend/`, `backend/`, `migrations/`, `docker-compose.yml`. Сейчас Rust-пакет (`Cargo.toml`, `src/`) находится в корне. Решение оставить его там или перенести в `backend/` принять явно с командой; на API это не влияет. В рамках этого ТЗ код не переносится.

Передать:

- воспроизводимые миграции и команду их применения к чистой БД;
- `.env.example` без реальных секретов;
- команды локального запуска Rust-сервера, PostgreSQL и frontend dev proxy;
- production build frontend и раздачу его assets сервером;
- конфигурацию одного VPS: reverse proxy/TLS, backend, PostgreSQL; допустим Docker Compose;
- команды запуска тестов, инструкции deploy/обновления;
- инструкцию администратора: скрыть UUID, создать backup, восстановить backup и проверить результат.

Предлагаемые группы конфигурации: `DATABASE_URL`, bind address, путь static assets, allowlist origins, настройки административной MFA-сессии/WebAuthn, лимиты штрихов/сообщений/областей/очередей, таймауты. Точные имена переменных определить в `.env.example`. Административные секреты не должны иметь frontend-префикс `VITE_`.

Readiness становится успешной только при готовой БД и применённой схеме; liveness не должен зависеть от наличия пользовательских штрихов. Всё запускается без платных внешних сервисов.

## 10. Порядок реализации

1. **Основа:** конфигурация, Axum/Tokio, SQLx pool, миграция, health/ready, PostgreSQL для локальной разработки.
2. **Домен:** валидация, bbox, ownership, выборка области, create/delete и идемпотентность.
3. **Realtime:** hello, последовательный обработчик мутаций, подписки, согласованный snapshot, буфер событий, ack/error.
4. **Интеграция:** mock fixtures из общего контракта, два браузера, reconnect, повторы и гонки snapshot.
5. **Эксплуатация:** лимиты, slow-client handling, закрытое скрытие, логи, TLS, backup/restore, документация.

Frontend может начинать по согласованным fixtures сразу; для первого совместного стенда нужны hello, пустой/многочастный snapshot, create/delete, ack/error и корректный `own`.

## 11. Тесты и критерии готовности

### Unit

- Валидация всех числовых границ, структуры точек, UUID, цвета, brush и секрета.
- Bbox для точки, round/square, наклонных концов, предельных координат.
- Проверка прав удаления и ownership публичных объектов.
- Семантическое сравнение payload для идемпотентности.
- Лимиты и безопасная обработка некорректных сообщений.

### Integration с настоящим PostgreSQL

- Миграции с нуля, индексы и поиск `box && box`, включая границы толстых линий.
- Создание/soft delete, сортировка и многостраничная загрузка плотной области.
- Чужое delete через прямой WS-запрос не изменяет данные.
- Повтор create с тем же UUID и payload; конфликт содержимого/владельца; повтор create после delete; повтор delete.
- Параллельные мутации проходят один обработчик, публикация только после commit.
- Ошибка/rollback не создают успешного ack/event.
- Создания и удаления на разных стадиях snapshot не теряются; read snapshot установлен до выбора страниц.
- Новая подписка во время старой загрузки не смешивает области.
- Переполнение буфера/медленный клиент вызывают resync или disconnect, а не тихую потерю.
- Перезапуск после commit до ack, повтор UUID и новый snapshot не создают дублей.
- Admin hide даёт тот же эффект у живых клиентов, что и пользовательское удаление.
- Секреты/digest не раскрываются в публичных payload и логах.

### Совместная приёмка

- Два независимых посетителя видят одни и те же сохранённые линии возле начала мира.
- Завершённый штрих первого появляется у второго без reload; удалить его может только первый или администратор.
- Reload сохраняет рисунок и сессионное право удаления; reconnect не теряет подтверждённое состояние.
- Загрузка ограничена областью и идёт порциями, корректна прозрачность через единый `seq`.
- Некорректные координаты, слишком большие сообщения и чрезмерная частота отклоняются.
- Чистая БД разворачивается миграциями, probes работают, backup реально восстанавливается.

Backend непосредственно закрывает AC-04–AC-07, AC-09–AC-14 исходника совместно с frontend там, где есть UI. AC-01–AC-03 и AC-08 — прежде всего frontend.
